How VS Code Extensions Should Be Built

Design Principles for Preventing “It Worked Yesterday, but Suddenly Broke”

One day, a VS Code extension began reporting the following error:

Could not find ripgrep binary

Yet ripgrep was installed.

It worked perfectly from the terminal:

which rg
rg --version

Both commands completed successfully.

Nevertheless, the extension continued to insist that the binary could not be found.

The immediate cause turned out to be simple: the extension was searching for ripgrep in locations where it no longer existed.

But the real lesson is not that adding one more search path fixed the problem.

Why was the extension designed so that a minor change in the host application’s internal directory structure could disable it completely?

This is not merely a Roo Code issue, nor is it limited to VS Code.

The same class of failure can affect IDE extensions, Electron applications, browser extensions, command-line integrations, database plugins, enterprise add-ons, automation tools, and software that embeds or invokes external binaries.

This incident provides a useful case study in how extensions should—and should not—be designed.

What Actually Happened

The extension depended on ripgrep, a high-performance text-search utility.

VS Code itself bundles a copy of ripgrep for its own search functionality. Rather than shipping and managing its own copy, the extension attempted to locate and reuse the binary bundled inside VS Code.

Its resolver searched paths resembling the following:

node_modules/@vscode/ripgrep/bin/
node_modules/vscode-ripgrep/bin/
node_modules.asar.unpacked/vscode-ripgrep/bin/
node_modules.asar.unpacked/@vscode/ripgrep/bin/

However, in the installed version of VS Code, the actual binary was located under a newer package and platform-specific directory:

node_modules.asar.unpacked/
  @vscode/
    ripgrep-universal/
      bin/
        darwin-arm64/
          rg

The binary existed. It was executable. It matched the operating system and CPU architecture. It produced a valid version response.

The extension simply did not know where to look.

The resolver therefore returned no path, eventually causing the extension to throw:

Could not find ripgrep binary

At first glance, this looks like a straightforward file-discovery failure. At the architectural level, however, it exposes a much deeper weakness.

The Fundamental Problem: Depending on Undocumented Internals

The most important failure was not the missing path.

It was the extension’s dependence on VS Code’s private internal directory structure.

Locations such as the following are not stable extension APIs:

appRoot/node_modules/
node_modules.asar.unpacked/
@vscode/ripgrep/
@vscode/ripgrep-universal/

They are implementation details of the host application.

Implementation details can change for many reasons: package restructuring, dependency replacement, Electron packaging changes, platform-specific bundling, security hardening, support for new CPU architectures, build-system changes, or startup-performance optimization.

An extension developer may inspect the VS Code installation, notice that a usable executable is present, and decide to reuse it.

That can work.

But there is a critical distinction:

A resource being visible does not mean its location or availability is part of a supported contract.

This distinction is fundamental to extension development.

The moment private implementation details are treated as public APIs, the extension inherits a dependency that the host application never agreed to preserve.

Public APIs and Observable Internals Are Not the Same Thing

A documented public API normally provides several expectations:

  • its intended use is documented;
  • compatibility is managed;
  • changes are announced or versioned;
  • supported behavior is defined;
  • consumers are explicitly permitted to depend on it.

An internal directory provides none of those guarantees.

The file happens to be here in this build.

That is not a durable interface.

An extension that relies on such a location may work today, pass local testing, and appear completely stable. Then the host application is updated.

The internal package name changes from:

@vscode/ripgrep

to:

@vscode/ripgrep-universal

The binary is moved under an architecture-specific directory:

bin/darwin-arm64/

The extension itself has not changed, yet it stops working.

This is how software can break without anyone modifying its source code.

Software Does Not Operate in a Static Environment

A common misconception is that unchanged software should continue behaving identically.

That is true only when its entire environment is also unchanged.

An extension may remain frozen while the host application, operating system, Electron, Node.js, package layouts, filesystem permissions, CPU architectures, signing requirements, security policies, remote development environments, and container runtimes continue evolving.

An archived extension is therefore not truly preserved.

Its source code is static, but its compatibility is gradually decaying.

Who Owns the External Binary?

Who is responsible for the external executable on which the extension depends?

Model 1: The Extension Bundles Its Own Binary

The extension distributes the required executable as part of its package.

It owns the version, supported platforms, CPU architectures, permissions, signing requirements, vulnerability updates, and distribution size.

This creates additional maintenance work, but the responsibility is clear.

Model 2: The User Installs the Binary

The extension declares ripgrep as an external prerequisite:

ripgrep 14 or later must be available on PATH.

The resolver can invoke rg --version and validate the result.

Model 3: The Extension Reuses the Host Application’s Private Copy

This was effectively the design used in the incident.

VS Code already ships ripgrep, so the extension can reuse it.

This appears efficient, but the ownership model becomes dangerously ambiguous.

The extension does not manage the binary, but still assumes that it will remain available in a specific undocumented location.

Borrowing Another Product’s Bundled Dependency Is Fragile

Reusing a binary already present in the host application can reduce download size and packaging complexity.

But those benefits come with an architectural cost: the extension becomes coupled to the host’s private packaging decisions.

If you depend on an undocumented host resource, design the feature under the assumption that the resource will eventually move, change, or disappear.

Binary Discovery Is a Dependency-Resolution Problem

return candidateA
    || candidateB
    || candidateC
    || candidateD

That may be adequate for a prototype. It is not adequate for a long-lived extension.

  1. A path explicitly configured by the user
  2. A binary bundled and managed by the extension
  3. A path supplied through a supported host API
  4. A validated binary found on the system PATH
  5. Known compatibility paths for specific host versions
  6. A structured diagnostic result explaining the failure

Undocumented host paths should be treated only as compatibility fallbacks.

Allow Users to Configure an Explicit Path

{
  "extension.ripgrepPath": "/opt/homebrew/bin/rg"
}

This is more than a convenience feature. It is an operational escape hatch.

Why PATH Fallback Matters

In this incident, a working ripgrep binary already existed at:

/opt/homebrew/bin/rg

The extension ignored it because its resolver did not search the system PATH.

which rg

or:

spawn("rg", ["--version"])

PATH resolution must be validated, but ignoring it entirely removed an obvious recovery route.

“The File Exists” Is Not the Same as “The Binary Works”

A robust resolver should verify that the file exists, is executable, supports the current platform and architecture, can be launched, and satisfies the required version range.

rg --version

Existence is only the beginning of validation.

Error Messages Should Contain the Investigation Trail

ripgrep resolution failed

Extension:
  Roo Code 3.54.0

Host:
  Visual Studio Code 1.130

Platform:
  darwin-arm64

Checked host paths:
  /Applications/.../@vscode/ripgrep/bin/rg
  /Applications/.../vscode-ripgrep/bin/rg
  /Applications/.../@vscode/ripgrep-universal/bin/darwin-arm64/rg

PATH lookup:
  /opt/homebrew/bin/rg

Validation:
  /opt/homebrew/bin/rg --version
  exit code: 0
  version: ripgrep 15.0.0

The quality of diagnostics often determines whether a problem takes five minutes or five days to resolve.

Do Not Collapse Every Failure into “Not Found”

BinaryNotFound
BinaryNotExecutable
BinaryArchitectureMismatch
BinaryVersionUnsupported
BinaryLaunchFailed
BinaryPathInvalid
HostLayoutUnsupported

Each category implies a different remedy. Coarse error classification leads directly to incorrect troubleshooting advice.

Version Compatibility Must Be Explicit

  • Minimum supported VS Code version
  • Known compatible and incompatible host versions
  • Supported operating systems
  • Supported CPU architectures
  • Expected external dependency versions
Extension: 3.54.0
VS Code: 1.130
Platform: macOS arm64

Archived Extensions Require a Compatibility Strategy

An archived extension should ideally be accompanied by a compatibility matrix, known host-version limitations, maintenance patches, migration guidance, reproducible build instructions, a documented dependency resolver, and a diagnostic command.

Archiving code preserves its source. It does not preserve the runtime environment on which it depends.

Test the Integration Boundary, Not Just the Function

A compatibility matrix should include VS Code Stable, VS Code Insiders, macOS arm64, macOS x64, Windows x64, and Linux x64.

The test should cover extension activation, binary resolution, binary execution, search operation, fallback behavior, and diagnostic output.

Why VS Code Insiders Testing Matters

On every pull request:
  VS Code Stable on primary platforms

On a scheduled basis:
  VS Code Insiders

Before release:
  Windows x64
  macOS arm64
  macOS x64
  Linux x64

Avoid Stale Resolution Caches

A cache should be associated with the host version, extension version, operating system, CPU architecture, resolved path, binary version, and validation timestamp.

Run Self-Diagnostics After Environment Changes

Extension: Run Diagnostics

The report should include environment details, dependency resolution attempts, resolved executable paths, validation results, and known compatibility warnings.

Automatic Recovery Should Be Safe and Transparent

A compatible system ripgrep installation was found at:

/opt/homebrew/bin/rg

Use this executable?

Automatic recovery should explain the change, be reversible, validate the selected binary, record the decision, and respect managed policies.

More Fallbacks Are Not Always Better

Explicit user configuration     High trust
Extension-bundled binary         High trust
Supported host API               High trust
System PATH                      Medium trust
Known host-internal layout       Low trust
Workspace-local executable       Untrusted by default
Full-disk search                 Avoid

The extension should disclose which source was selected.

External Binary Discovery Is Also a Security Boundary

A secure resolver should avoid auto-executing workspace-local binaries, display the resolved absolute path, require consent for lower-trust sources, resolve symlinks, verify signatures or hashes where appropriate, restrict discovery to trusted directories, and integrate with VS Code Workspace Trust.

A More Robust Architecture

RipgrepResolver
  ├─ Check explicit user configuration
  ├─ Check the extension-bundled binary
  ├─ Query supported host capabilities
  ├─ Search and validate the system PATH
  ├─ Check known compatibility layouts
  └─ Return a structured diagnostic result
type BinaryResolution = {
  path?: string
  source?: "configured" | "bundled" | "host-api" | "path" | "host-internal"
  version?: string
  platform: string
  architecture: string
  attempts: ResolutionAttempt[]
  error?: ResolutionError
}

Seven Principles for Building Durable Extensions

Principle 1: Never Treat Host Internals as Public APIs

A visible internal file is not a stable contract.

Principle 2: Make Dependency Ownership Explicit

Decide whether the extension, the user, or a supported host API owns each external dependency.

Principle 3: Design Binary Discovery as Dependency Resolution

Use ordered strategies, trust levels, validation, and structured failure information.

Principle 4: Validate Executability, Not Mere Existence

A file is not a usable dependency until it has been launched and verified.

Principle 5: Include the Search Process in Diagnostics

Record what was checked, what was found, what was rejected, and why.

Principle 6: Continuously Test the Host Integration Boundary

Test real extension behavior across host versions, operating systems, and CPU architectures.

Principle 7: Assume Dependencies Will Change

Provide explicit paths, fallbacks, compatibility layers, self-diagnostics, and recovery mechanisms.

A One-Line Fix Can Reveal an Architectural Problem

@vscode/ripgrep-universal/bin/darwin-arm64/

The small patch exposed much larger issues: dependence on undocumented internals, unclear dependency ownership, insufficient fallback behavior, weak diagnostics, missing compatibility management, inadequate integration testing, architecture-specific assumptions, security risks in executable discovery, and the maintenance burden of archived extensions.

The size of a code change does not indicate the depth of the design failure.

Code That Works Is Not the Same as Code That Keeps Working

Writing code that works in the current environment is relatively easy.

Writing code that continues to work while its environment changes is much harder.

Extension development is not simply the act of adding functionality to a host application.

It is the act of maintaining a contract with a system controlled by someone else.

Conclusion

The immediate cause of this incident was a changed ripgrep path.

The fundamental cause was that the extension treated a changeable, undocumented part of the host application as a stable dependency.

When that assumption failed, the extension had no PATH fallback, no explicit-path configuration, no supported API-based resolution, insufficient diagnostics, no clear incompatibility warning, and no robust recovery mechanism.

When your software depends on something you do not control, design for change by providing detection, validation, fallback, diagnostics, and recovery.

An extension is not merely a small program running inside a larger application.

It is software that must remain connected to an independently evolving system.

That is why boundary design matters more than the convenience of a hard-coded path.
